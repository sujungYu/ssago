# 결정·문서 충돌·미정 사항

## 구현 중 내린 가정 (정책서에 없거나 모호해서 화면 동작만 정함)
1. 알림함은 만들지 않았다. S-02는 알림 링크 도착 화면이며, 대상 상태가 알림 이후 바뀌었으면 최신 상태 안내를 붙여 이동한다.
2. 결제 “결과 확인 중” 상태에서는 새 결제를 만들지 않는다(ERR-PAY-03). 조회(`refreshPayment`)만 허용.
3. 그룹이 종료되면 결제 대기 고객의 승인에 `recheck`(새 그룹 조건)가 붙고, 동의해야 결제할 수 있다. 새 그룹은 먼저 결제한 고객이 기준이 된다.
4. 취소 확정 시 확인한 환불 금액(`expectedRefund`)을 함께 보내 금액이 바뀌었으면 거절(ERR-CAN-01). 화면은 금액·조건 버전이 바뀌면 동의를 초기화한다.
5. 지연 대응의 무료 변경·무료 취소는 요청/취소가 완료될 때 지연 안내가 종결되며, 사용자가 직접 고른 “기다리기”만 선택으로 기록한다.
6. ~~업체 사유 변경 제안을 거절하면 공제 없는 전액 환불 취소로 처리한다.~~ → 2026-10-12 변경: 거절해도 기존 예약을 유지하고 자동 취소·환불하지 않는다. 고객이 다른 일정 협의 또는 업체 사유 무료 취소를 직접 선택한다(아래 ‘방문 시간 기준’).
7. 취소·일정 변경 버튼은 방문 전(`scheduled`)에만 노출한다(작업 시작 후·후속 방문 취소 정책은 미정).
8. 비교 묶음(같은 작업을 여러 업체에 요청)의 식별 방식과 UI는 미정이라 “다른 업체에도 요청” 버튼으로 같은 묶음 ID를 이어 쓰는 방식으로 가정했다.
9. 예상 총액은 `업체 견적 합계 + 부품 예상 + 내 예상 출장비`이며 “최종 금액 아님”을 항상 병기한다.
10. 요청 가능 날짜 최소값은 오늘+48시간(마감 규칙을 맞추기 위한 임시 값).

## 방문 시간 기준 (2026-10-12 변경)
고객은 가능한 시간 범위를 제출하고, 업체는 그 안에서 방문 시각을 제안한다. 고객이 승인 조건을 확인하고 예약금을 결제하면 해당 시각으로 예약이 확정된다. 상세 기준은 spec.md 4.1절.
1. **확인한 기존 구조**: 승인·예약·변경 제안·지연 모두 고객 가능 시간 범위(`visitWindow`, `originalWindow`, `newVisitWindow`, 변경 제안의 `window`)만 있었고 업체 제안 방문 시각 필드는 없었다. 그래서 내 예약에 ‘13:00–16:00’ 같은 범위가 방문 시간처럼 보였다.
2. **바꾼 구조**: `Approval.visitTime`(업체 제안), `Booking.visitTime`(예약 확정)·`Booking.customerSlots`(요청 시 가능 시간, 수정하지 않음)·`Booking.scheduleChanges`(변경 기록), `ChangeProposal.oldVisit.time`/`newVisit.time`(+ 고객 요청의 `newVisit.wishSlot`), `DelayNotice.originalVisitTime`, `Recheck.newVisitTime`. 규칙은 `src/domain/visitTime.ts`.
3. **추정 금지**: 방문 시각이 없으면 범위로 채우지 않고 ‘방문 시각 확인 필요’로 표시한다. 그룹 종료로 생긴 새 조건(`recheck`)은 같은 업체·같은 날짜라 업체가 제안했던 시각을 그대로 옮긴다(없으면 비워 둔다).
4. **업체 화면 없음**: 업체 승인·변경 제안은 목업 시드와 개발 도구로만 만든다(2026-10-12부터 화면의 DEV 버튼·패널은 없고 화면 없는 훅 `window.__sagoDev`만 있다). 개발 도구는 방문 시각을 직접 입력받고, 고객 가능 시간 밖이면 최초 승인을 거절한다.
5. **목업 DB 저장 키 v2**: 구조가 바뀌어 이전 sessionStorage 목업 DB(`on-gimae/mock-db/v1`)는 읽지 않는다.
6. **데이터 보완 필요(실제 연동 시)**: 승인·예약 테이블에 업체 제안/확정 방문 시각 컬럼, 변경 이력(기존 일정·사유·고객 동의 시각) 저장, 방문 시각 누락 승인을 막거나 보완 요청하는 업체 입력 검증.

## 예약 금액·결제 통합 카드 (2026-10-12)
1. **확인한 가격 데이터:** 작업비는 `ApprovedTask.estimate`(타입 주석 “업체 견적(작업비)”, 작업별, null = 현장 확인), 부품·자재는 `Approval.partsEstimate`로 분리돼 있어 작업비에 자재가 포함됐다고 볼 근거는 없다. 최종 내역도 작업비·부품·자재비·출장비를 따로 둔다.
2. **가정(보완 필요):** 예약 후 별도 동의하는 맞춤 자재(`MaterialOffer`)는 `partsEstimate`에 포함되지 않은 별도 건으로 본다(승인 materialNote “맞춤 자재는 별도 안내 후 동의” 기준). 실제 데이터에서 이 포함 관계를 필드로 명시해야 한다.
3. **업체 할인:** `discountNote`는 문구만 있고 금액이 없다. 예상 총금액에 반영하지 않고 ‘최종 정산에서 반영’으로 표시한다. 할인 금액 필드가 필요하다.
4. **마감 시 세대 수 저장:** 그룹에 `finalHouseholds`를 추가했다. 마감 후 취소는 현재 참여 세대(`confirmedHouseholds`)만 줄이고 확정 출장비·분담 기준은 그대로 둔다(이전에는 마감 후 취소 시 현재 세대 수도 줄이지 않아 ‘참여 확정 세대’가 실제와 달랐다).
5. **최종 정산과의 관계(남은 확인):** 자재 선결제는 정산 잔액에 포함된다. 최종 내역에 해당 맞춤 자재 항목이 빠지면 그 금액이 환불로 계산되므로, 업체 최종 내역 입력 시 선결제 자재를 항목으로 포함하는지 검증이 필요하다(업체 입력 경로가 없어 이번 범위에서는 표시 기준만 정함).

## 주소 설정·저장·자동 입력 (2026-10-12)
1. **확인한 기존 구조:** 탐색 주소는 이 탭의 화면 상태(sessionStorage)에만 있었고, 요청은 건물 id(`addressId`) + 상세 주소(`addressDetail`)를 저장하고 화면은 주소 목록을 다시 조회해 보여줬다. 예약은 상세 주소를 요청에서 읽었다. 신청서의 ‘변경’은 업체 찾기 탐색 주소 자체를 바꿨고, 내 정보에는 목업 고객 주소(`customer.addresses`)가 있었다.
2. **발견한 데이터 문제:** 시드 요청의 상세 주소 기본값이 항상 ‘301동 1204호’라 다른 건물(푸른숲 2단지·달빛길) 요청·예약에도 햇살마을 동·호수가 붙어 있었다. 건물별로 명시하도록 고쳤다.
3. **바꾼 구조:** 탐색 주소(`exploreAddressId`, 사용자별), 재사용 방문 주소(`savedVisitAddress`, 사용자당 1개), 요청·예약 방문 주소 스냅숏(`visitAddress`). 주소 목록(`Address`)에서 상세 주소를 뺐다. 목업 DB 저장 키 v3.
4. **같은 건물 판단:** 건물 식별자 + 기본 주소가 모두 같을 때만. 같은 단지의 다른 건물(시드 ‘햇살마을 3단지 상가동’)은 공동 예약 조건(동일 단지)은 같아도 상세 주소를 자동 입력하지 않는다.
5. **제출 실패 재현:** 목업 설정에 ‘다음 저장 1회 실패’(`failNextWrite`)를 추가했다(개발 도구). 실패 시 요청·재사용 주소 모두 바뀌지 않는다.
6. **보완 필요(실제 연동 시):** 사용자별 탐색·재사용 주소 테이블과 RLS, 주소 공급자 기준 건물 식별자, 요청·예약 방문 주소 컬럼(스냅숏). 지금은 목업이라 같은 탭 안에서만 유지된다.

## 미정(결정하지 않고 표시만 한 것)
- 몇 분 지연부터 무료 변경·취소 선택권을 줄지, 재지연 처리 — 분 단위 기준·자동 환불 규칙을 정하지 않았다. 지연 화면은 업체가 지연을 알린 예약에 기존 선택지만 보여준다.
- 방문 시각이 없는 승인의 결제 허용 여부 — 지금은 막지 않고 ‘방문 시각 확인 필요’만 표시한다.
- 새 일정 예약금이 기존보다 적어 남는 금액(`excessUndecided`)의 처리 — 화면에 “아직 정해지지 않았어요”로 안내.
- 결제수단·PG, 로그인 방식, 알림 채널·알림함, 업체 정보 관리 범위, 자동 위치 수집.
- 약관·개인정보 처리방침 실제 문안(법률 검토 전) — `/guide`는 서비스 규칙 요약.
- 리뷰 노출 정책(작성자 마스킹 외), 사진 업로드 저장소 — 목업은 파일명만 보관.
- 승인 경계 시각(마감과 같은 시각 등) — 상태 플래그를 우선해 판단.

## 로그인 없는 데모 (2026-10-12 변경 — 아래 2026-10-08 인증 결정을 대체)
1. **확인한 연결 현황:** 실제 DB 연결은 Supabase Auth 코드뿐이었고(이 작업 폴더에는 URL·키 없음 → 임시 데모 로그인으로 동작), 요청·예약·주소·업체 데이터는 모두 목업이었다. 인증을 제거해도 공개되는 실제 데이터는 없다.
2. **바꾼 것:** 인증 가드·로그인 리다이렉트·세션 확인 대기 제거, 인증 화면(로그인·회원가입·가입 완료·비밀번호 재설정)·내 정보의 이메일·로그아웃 제거, 이전 인증 주소는 업체 찾기로 이동. 인증 전용 코드(`src/app/auth.tsx`, `src/features/auth`, `src/data/auth`, `src/data/repositories/auth.ts`, `src/domain/auth.ts`, 비밀번호 입력 컴포넌트, 인증 오류 코드·스타일)와 `@supabase/supabase-js`·Supabase/인증 환경 변수를 다른 사용처가 없음을 확인하고 제거했다.
3. **사용자 구분 유지:** 요청·예약·주소는 사용자 id를 직접 쓰지 않고, 목업 DB 소유 계정·계정별 화면 상태·필터 기록의 계정 표시만 계정을 구분한다. 이 구조를 지우지 않고 고정 가상 데모 고객 id(`demo-customer`, `src/app/account.ts`)로 유지한다.
4. **유지 범위 변화:** 데이터는 여전히 탭의 sessionStorage. 로그아웃이 없어져 로그아웃으로 지워지는 경우가 사라졌고, 탭·브라우저를 닫으면 처음 데모 데이터로 시작한다(이전과 같음).
5. **제한:** 데모 범위이며 실제 다중 사용자 서비스의 접근 제어를 대체하지 않는다. 실제 데이터 연결 시 인증·RLS를 함께 도입한다(익명 방문자를 실제 계정 하나에 묶지 않음, RLS 해제·전체 공개 금지, secret 키 브라우저 금지).

## (대체됨) 인증·앱 진입 (2026-10-08 변경)
### 정한 것
1. **로그인 후 앱 이용**: 인증 화면(로그인·회원가입·가입 완료·비밀번호 재설정 3종) 외 모든 화면은 `RequireAuth` 아래에 있다. 알 수 없는 주소(`*`)도 로그인 후에만 안내한다. 세션 확인이 끝날 때까지 `AuthProvider`가 로딩 화면만 그려 내부 화면이 먼저 보이지 않는다.
2. **Supabase Auth 이메일·비밀번호 실제 연결**, 데이터는 목업. 소셜 로그인 제외.
3. **가입 후 로그아웃**: 이메일 확인이 꺼진 설정에서 가입과 함께 세션이 생기면 즉시 로그아웃하고 가입 완료 → 로그인 화면으로 보낸다. 가입 중 생긴 세션의 인증 이벤트는 화면에 전달하지 않는다(내부 화면이 잠깐 열리지 않게).
4. **세션 유지**: Supabase SDK 기본값(localStorage 저장, 자동 갱신)을 쓴다. 앱 시작 시 저장된 세션을 `getUser`로 서버에 확인해 무효(401·403·세션 없음)면 지우고 로그인 화면, **네트워크 실패면 저장된 세션으로 진입**한다(보호 대상이 목업이라서). 세션 확인 자체가 네트워크로 실패하면 로그인 화면이 아니라 “다시 시도” 화면을 보여 준다.
5. **로그아웃은 이 기기만**(`scope: 'local'`). SDK는 서버 호출이 실패해도 로컬 세션을 지운다.
6. **계정 전환·로그아웃 시 초기화**: 목업 상태(sessionStorage 목업 DB)를 새 데모 시드로 바꾸고, 방문 지역(sessionStorage)을 지우며, 화면 트리를 계정 단위로 다시 만든다(조회 캐시·입력 중 상태 제거). 같은 계정의 새로고침은 목업 진행 상태를 유지한다. **모든 계정은 같은 가상 데모 데이터에서 시작**한다(실제 사용자별 데이터가 아님).
7. **오류 구분**: 자격 오류(“이메일 또는 비밀번호를 확인해주세요”), 이메일 미확인, 비밀번호 정책 위반, 이미 가입된 이메일, 요청 제한, 네트워크 오류(연결 실패·5xx, “다시 시도” 버튼)를 나눈다. 서버 원문 메시지와 비밀번호는 화면·로그에 쓰지 않는다.
8. **비밀번호 재설정**: 요청 결과는 계정 유무와 관계없이 같은 안내. 메일 링크(복구 세션)로 들어온 경우에만 새 비밀번호를 받고, 변경 후 로그아웃 → 로그인 화면.
9. 로그인 성공은 항상 업체 찾기(`/`)로 이동한다(원래 보려던 화면으로 돌아가는 기능은 이번 범위 밖).

### 출시 전 다시 검토 (미정)
- **이메일 확인 정책**: 데모는 Supabase “Confirm email”을 끈 구성을 전제로 한다. **데모 전용이며 출시 전 반드시 재검토**(스팸 가입·타인 이메일 도용 방지).
- **비밀번호 정책**: 최소 길이·조합 규칙·유출 비밀번호 차단은 Supabase 설정으로 정하고 `VITE_AUTH_PASSWORD_MIN_LENGTH`를 맞춘다. 현재 코드 기본값 6은 Supabase 기본값일 뿐 정책이 아니다.
- **세션 저장 위치·유지 기간**: localStorage(SDK 기본) 유지 여부, 비활성 만료·다른 기기 로그아웃.
- 약관·개인정보 동의(필수/선택, 만 14세 확인, 동의 이력 저장), 회원 탈퇴·정보 수정, 연락처 수집 시점, 업체 계정.
- 이미 가입된 이메일로 가입할 때의 안내(현재 “이 이메일로는 가입할 수 없어요”는 이메일 확인이 꺼진 설정에서 가입 여부를 드러낼 수 있음 — 확인 정책과 함께 결정).
- **데이터 권한**: 지금 보호 대상은 목업이다. 실제 데이터를 연결할 때 서버·RLS 검증 없이 출시하지 않는다(출시 차단 조건).
